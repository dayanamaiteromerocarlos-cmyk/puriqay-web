# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Puriqay is a volunteer-management single-page app for a Peruvian volunteering organization (UI copy is entirely in Spanish, es-PE locale for dates/times). It is a pure client-side React app: there is no backend/API code in this repo — all auth, data, and business logic talk directly to Supabase (Postgres + Auth) from the browser.

## Two repositories

This repo is the **frontend only**, and it is **public**. Everything that defines the database lives in a separate, **private** backend repo (`puriqay-backend`; checked out as the sibling folder `../puriqay-backend`): the Supabase migrations (schema, RLS policies, grants, triggers), the Auth email templates, the schema snapshot (`docs/database-schema.md`) and `PENDIENTES.md`, the checklist of out-of-code configuration and security work.

Because this repo is public, do not write security findings, unpatched weaknesses or operational checklists here — they go in the backend repo. A database change is a migration there, not SQL pasted into this repo.

## Commands

- `npm run dev` — start the Vite dev server.
- `npm run build` — `tsc -b && vite build`. TypeScript project references (`tsconfig.app.json`/`tsconfig.node.json`) have `noUnusedLocals`/`noUnusedParameters` on, so the build fails on unused imports/vars, not just type errors.
- `npm run lint` — runs `oxlint` (config in `.oxlintrc.json`). This repo uses oxlint, not ESLint — there is no `.eslintrc`.
- `npm run preview` — serve the production build locally.
- `npm run deploy` — build with `.env` (production Supabase, never `.env.local`) and upload `dist/` to the Cloudflare Pages project `puriqay-web` as production (app.puriqay.org). `npm run deploy -- --preview=<rama>` uploads a preview at `<rama>.puriqay-web-9lc.pages.dev` instead (needed to test the PWA on phones: a service worker requires HTTPS); it still talks to the production database.
- There is no test framework configured in this repo (no test runner, no test files).

## Environment

`src/lib/supabase.ts` reads `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` from `.env` and constructs the single shared `supabase` client used everywhere. There's no other backend config.

## Architecture

**Routing is minimal; `Dashboard` is the real app shell.** `src/App.tsx` (react-router-dom v7) declares the public routes (`/` → `Login`, `/register`, `/forgot-password`, `/reset-password`) and `/dashboard/*` → `Dashboard`; everything else redirects to `/`. Once logged in, `Dashboard` (`src/components/Dashboard.tsx`) fetches the caller's `profiles` row once (`role`, `area`, `is_active`, names, `qr_token`) and then switches between feature components with a sidebar. The open tab lives in the URL, not in state, so the browser's Back button walks through the visited tabs and a reload keeps the tab: `activeTab` is read from `/dashboard/<dirección>` through the `DIRECCIONES` table (internal tab id → Spanish URL segment, e.g. `volunteers` → `voluntarios`), and an empty, unknown or not-permitted segment (`PERMISO_TAB`) is replaced with `/dashboard/inicio`. Login, registration and logout navigate with `replace`, so Back from the dashboard never returns to the login, and `Login` jumps to the dashboard when a session already exists. To add a dashboard section: add a component in `src/components`, a tab id plus its `DIRECCIONES` entry (and `PERMISO_TAB` if it is not for everyone), a `<SidebarItem>` entry, and a conditional render block in `Dashboard.tsx`. The default tab after login is `inicio` (`Inicio.tsx`: hours, upcoming jornadas, last activity); `inicio` and `mis_asistencias` (`MisAsistencias.tsx`, the attendance history) are shown to everyone. One tab is outside the sidebar list: `perfil` (`MiPerfil.tsx`, where anyone edits their own editable columns), opened from the user's short name shown above "Cerrar Sesión". "Detalle de Jornada" (`JornadaDetalle.tsx`) is not a tab either: "Ver detalles" in Inicio, Próximas Jornadas and Jornadas navigates to `/dashboard/<dirección>/jornada/<id>` under the tab it came from, and its "Volver" link goes back one history entry (or, when the detail was opened from a direct link, replaces it with that tab). On phones the sidebar becomes a drawer opened from the 72px header; opening it pushes a history entry marked `state.menu`, so Back closes it, and choosing a tab from it replaces that entry. Shared visual pieces (`EncabezadoPagina`, `ChipLinea`, `TarjetaJornada`, `Modal`, buttons, `inputClass`/`labelClass`) live in `JornadaUI.tsx`, and the jornada helpers (dates, Lima-relative status, history) in [src/lib/jornadas.ts](src/lib/jornadas.ts).

**Authorization is role/area-based; the UI side lives in [src/lib/permisos.ts](src/lib/permisos.ts).** Three columns on `profiles` drive it:
- `role`: `ADMIN` | `COORDINADOR` | `VOLUNTARIO`
- `area`: one of the rows of the `areas` table (a closed catalog — a foreign key rejects anything else), mirrored as the `AREAS` constants in `permisos.ts`: `"Gerencia General"`, `"Tecnologías de la Información"`, `"Gestión Humana"`, `"Gestión de Proyectos Sociales"`, `"Comunicación y Difusión"`, `"Finanzas y Logística"`. Internal staff always have one; external volunteers have `null`. Use the constants, never a retyped string.
- `is_active`: `false` removes every internal-staff permission.

`permisos(perfil)` turns those into flags (`gestionaJornadas`, `veDatosPersonales`, `editaRolArea`, `supervisaMarketing`, `veMarketing`, ...) that `Dashboard.tsx` uses for the sidebar and components use for buttons (`MarketingBoard` loads its own profile and asks `permisos(...)`; `JornadaDetalle` offers internal staff "No asistiré" with a justification, while a `VOLUNTARIO` only signs up). This gating is UI-only: the database enforces the same rules with RLS policies and functions versioned as migrations in the backend repo, and if the two disagree the database wins — when a rule changes, change it there first and then mirror it in `permisos.ts`.

Consequences for queries: reading `profiles` returns other people's rows only to whoever may see personal data, so to show *names* of other people use the `perfiles_basicos` view (`id`, names, `role`, `area`, `is_active`) — `fetchNombres(ids)` in `permisos.ts` does it for a list of ids; don't embed `profiles(...)` in a select. Role/area changes go through the `cambiar_rol_area` RPC and activating/deactivating someone through `cambiar_estado` (never an `update` on `profiles`); the dropdown options come from `opciones_rol_area`, so the UI never re-implements who may edit whom. Both RPCs write to `perfiles_cambios`, shown by `HistorialCambios.tsx` inside the Voluntarios tab.

**Data model** — the full column-by-column snapshot is `docs/database-schema.md` in the backend repo (hand-maintained despite its "generado automáticamente" header; update it there when the schema changes). The tables the frontend touches:
- `profiles` — one row per Supabase auth user (`id` = auth user id). Holds `role`/`area` plus the volunteer application data displayed in `VolunteerList.tsx` (contact info, emergency contact, study center, medical conditions, shirt size, geolocation). Also holds `qr_token`, the value encoded into a volunteer's QR credential (Dashboard's "Mi Código QR" tab, via `react-qr-code`). Onboarding is two-phase (see below) so most of these advanced columns are nullable and may be empty right after signup.
- `locations` — partner sites where activities happen (`Locations.tsx`). `status` is `ACTIVO` or `ARCHIVADO`: everyone else reads sites through the `locations_publicas` view (name, district, meeting point, action line, address, instructions and Maps link; no contact data), via `fetchLugaresPublicos` in `src/lib/jornadas.ts`, and the coordinator's name of a jornada through the `nombre_coordinador(jornada)` RPC. Archiving hides a site from the new-jornada dropdown (which only loads `ACTIVO`) but keeps its jornadas and history, and it can be restored. Archive/restore/delete are gated by `permisos().archivaLugares` (the DB enforces it with `borra_lugares()` and a trigger); a site can only be deleted while it has no jornadas — the DB refuses otherwise.
- `jornadas` — a scheduled activity/shift at a `location` with a coordinator (created, edited and deleted in `Jornadas.tsx`, listed in `AvailableJornadas.tsx` and opened in `JornadaDetalle.tsx` for RSVP). Create and edit share the `campos(...)` form. A jornada with `asistencias` cannot be deleted and its date, times and `valid_hours` cannot change (the DB enforces both; the UI disables the button and locks those fields using a count of `asistencias` per jornada). Deleting one without attendance also deletes its `inscripciones`. No jornada can be created in, or moved to, an archived site.
- `inscripciones` — a volunteer's RSVP to a `jornada` (`status` = `ASISTIRÁ`/`NO ASISTIRÁ`, plus justification fields required when internal staff can't attend); written by `JornadaDetalle.tsx`. The database enforces its own rules, so the client must not depend on bending them: a person can only insert/update their own row, and only while the jornada's date is today or later; rows cannot be deleted from the app; `NO ASISTIRÁ` requires `justification_type`; and `has_changed`/`created_at`/`updated_at` are computed by a trigger (whatever the client sends for them is ignored). The full list is in the backend repo's `docs/database-schema.md`.
- `asistencias` — actual check-in records. `AttendanceScanner.tsx` scans a QR (`@yudiel/react-qr-scanner`), looks up the person with the `buscar_por_qr(token, jornada)` RPC (returns only name and whether they had signed up), then inserts a row; the "Esperados" counter comes from `contar_esperados(jornada)` because other people's `inscripciones` aren't readable by all internal staff; a unique-violation (`error.code === '23505'`) is handled explicitly as "already checked in today."
- `marketing_tasks` — content-calendar items for the `"Comunicación y Difusión"` area (`MarketingBoard.tsx`), with status pipeline `Pendiente → En Revisión → Observado/Publicado`; `draft_date` is auto-derived client-side as `post_date - 7 days`. `references` (max 3, enforced by a DB check constraint) is a reserved SQL keyword — always double-quote it (`"references"`) in raw SQL. `submission_link` is filled in by the assignee via a modal when they click "Enviar a Revisión" (not by the supervisor at task-creation time). `extension_days` tracks how many days a supervisor has pushed out `draft_date` via the "Extender Plazo" control (an inline number input, not a fixed increment). `is_active` is a soft-delete flag — the board's fetch always filters `eq('is_active', true)`, and "Archivar" just flips it to `false` rather than deleting the row. "Borrar" (supervisors only, for test tasks) really deletes and asks twice: a `confirm()` and typing the exact title.

**Onboarding is two-phase, gated by a blocking modal, not by `Register.tsx`.** `Register.tsx` only collects the frictionless minimum at signup (`first_name`, `last_name`, `email`, `password`, `birth_date`, `phone`) — everything else on `profiles` (`document_id`, `emergency_phone`, `study_center`, `career`, `address`, `medical_conditions`, `shirt_size`, plus best-effort geolocation) is deferred. `Dashboard.tsx` re-checks these `ADVANCED_PROFILE_FIELDS` on every login **only for `COORDINADOR`/`ADMIN`** (external `VOLUNTARIO` accounts are never asked for them) and, if any is empty, renders `CompleteProfileModal.tsx` as a full-screen, non-dismissable overlay (`fixed inset-0 z-[100]`, no close button) on top of the whole app shell until the user submits them. If you add a new required field to this advanced set, update `ADVANCED_PROFILE_FIELDS` in `Dashboard.tsx` and the matching form field in `CompleteProfileModal.tsx` together — they're two separate literals, not derived from one schema.

**No shared data/state layer.** There's no Redux/Zustand/Context/React Query — every feature component fetches and mutates Supabase directly inside its own `useEffect`s and handlers, keeping results in local `useState`. Follow this per-component pattern for new features rather than introducing a state library.

**Design rules: read [docs/sistema-de-diseno.md](docs/sistema-de-diseno.md) before touching any UI.** It holds the design-system rules (control borders use `pq-border`, never `pq-cream-dark`; radii 12/20; title weights; no gradients; Markus usage) and the patterns agreed for the redesigned views (sidebar, mobile header and drawer, buttons, modals, chips, cards, load error).

**Styling: Tailwind v4 via `@tailwindcss/vite`**, config is CSS-first — there is no `tailwind.config.*` or `postcss.config.*`. The brand palette is defined once in [src/index.css](src/index.css) under `@theme` as custom tokens (`--color-pq-teal`, `-teal-50`, `-teal-dark`, `-teal-deep`, `-brand`, `-ink`, `-ink-muted`, `-cream`, `-cream-dark`, `-border`, `-marku`, `-marku-50`, `-marku-ink`, `-error`, `-error-50`, `-navy`, plus `--shadow-pq-card`/`--shadow-pq-focus` and the `font-sans` (Poppins) / `font-display` (Montserrat) families loaded in `index.html`) and consumed everywhere as `bg-pq-*`/`text-pq-*` utilities — reuse these tokens instead of hardcoding new colors. Their values come from the "Puriqay" design system (a Design System artifact in Claude, kept outside this repo); each token's comment names its design-system equivalent (`pq-teal` = `brand-600`, `pq-cream` = `surface`, ...). Errors use `pq-error`, success `pq-teal`, warnings `pq-marku-*`; the categorical badges (action lines in `catalogs.ts`, marketing status chips) keep distinct Tailwind hues on purpose. `FondoParticulas` hardcodes its own RGB colors for the canvas. `src/App.css` is unused leftover Vite-template boilerplate (not imported anywhere).

**Screenshots:** `npm run capturas` (`scripts/capturas/capturar.mjs`, Playwright) logs in with each test account of the backend's local seed, visits every sidebar tab and saves PNGs to `scripts/capturas/salida/` (gitignored). It needs `npm run dev` running against a **local** Supabase loaded with that seed (point the app at it with a gitignored `.env.local`) — never production.

**Feedback conventions:** `react-hot-toast` is the standard for success/error messages, with a single `<Toaster>` styled once in `App.tsx`. For destructive or archiving actions use `ConfirmDialog.tsx` rather than `confirm()` (`MarketingBoard` and `VolunteerList` still use `confirm()`). When a write may be blocked, chain `.select('id')` and treat 0 rows as "no permission" (RLS answers OK with no rows), and translate a delete blocked by dependent rows with `esBorradoBloqueado(error)` from `src/lib/dbErrors.ts` (Postgres 17 in production answers `23503`, newer versions `23001`).

**Form validation lives in [src/lib/validations.ts](src/lib/validations.ts)** — shared `PATTERNS`/`TITLES` consumed as HTML5 `pattern`/`title` attributes by `Register.tsx`, `CompleteProfileModal.tsx` and `Locations.tsx`. Two traps, both of which silently disable validation rather than erroring: (1) write character classes explicitly (`[0-9]`, never `\d`) because `"\d"` in a JS string collapses to `"d"`; (2) escape `-` and `/` inside a class (`\-`, `\/`) because browsers compile `pattern` with the regex `v` flag, where they're reserved — and when the pattern fails to compile the HTML spec says to ignore it entirely, leaving the field with *no* validation, no console error. The escapes look redundant (they would be under the older `u` flag) — don't "clean them up". These are client-side only and trivially bypassed; they're for typo prevention, not enforcement.

**"Today" means today in Lima.** When a query needs the current date (e.g. `AvailableJornadas` filtering `jornadas.date >= today`), use `todayInLima()` from [src/lib/dates.ts](src/lib/dates.ts). Never derive a date from `new Date().toISOString()`: that is the UTC date, which is already "tomorrow" from 7 p.m. Peru time — the bug that used to hide same-day jornadas every evening. `AttendanceScanner` also uses it, and only lists jornadas whose date is exactly today. For arithmetic on a `YYYY-MM-DD` string, parse it at local noon (`new Date(value + 'T12:00:00')`) as `MarketingBoard` does, so the day cannot shift.

**Email templates:** the Supabase Auth email templates live in the backend repo (`supabase/email-templates/`) — they are **not** compiled with the app; they are pasted by hand into Supabase under `Authentication → Emails`. What matters on this side is the contract: they read Go-template vars such as `{{ .Data.first_name }}`, which come from the `options.data` metadata that `Register.tsx` sends in `signUp`, so renaming those metadata keys breaks the emails (and the `handle_new_user` trigger that copies them into `profiles`).

**Password recovery:** `ForgotPassword.tsx` (`/forgot-password`) calls `resetPasswordForEmail` with `redirectTo: window.location.origin + '/reset-password'`, and `ResetPassword.tsx` (`/reset-password`) waits for the recovery session and calls `updateUser`. Because the redirect is built from the current origin, any host that serves the app (localhost, Pages previews, the production domain) must be allowed in Supabase's Redirect URLs — use wildcard entries (`https://host/**`) rather than one per route. The allow-list itself is dashboard config tracked in the backend repo, not here.

**Deployment:** `public/_redirects` (`/* /index.html 200`) rewrites all paths to `index.html`, i.e. this is hosted as a static SPA on a Netlify/Cloudflare-Pages-style host. Keep client-side routing working under that rewrite-everything-to-index assumption.

**PWA:** `vite-plugin-pwa` (configured in `vite.config.ts`) generates `manifest.webmanifest` and a Workbox `sw.js` at build time; there is no service worker under `npm run dev`, so test it with `npm run build && npm run preview` (the `puriqay-web-preview` entry of `.claude/launch.json`). The SW precaches only the build output and has no `runtimeCaching` — Supabase responses carry personal data and must never be cached; keep it that way. `globPatterns` (`js,css,html,png,svg`) deliberately leaves out the Markus animation in `public/media/dragon/` (WebM/WebP, several MB; see `docs/animacion-markus.md`): the browser fetches it only when it plays. `registerType: 'prompt'`: `ActualizacionApp.tsx` (mounted in `App.tsx`) checks for a new deploy hourly and on returning to the foreground, and shows a toast with "Actualizar"; it never reloads on its own. `public/_headers` keeps `sw.js`, `index.html` and the manifest uncached, and `scripts/deploy.mjs` refuses to deploy if the PWA files are missing from `dist/` (with `_redirects`, a missing file silently answers `index.html`). `start_url` is `/dashboard` so a logged-in user lands on Inicio without the login flashing first (`Login` also redirects an open session, but only after rendering). The icons in `public/` (`pwa-*.png`, `apple-touch-icon.png`, `favicon.png`) are generated from `scripts/iconos/isotipo-p.png` by `node scripts/iconos/generar.mjs` — regenerate rather than editing them. `index.html` deliberately has no `viewport-fit=cover`, so iOS keeps the installed app inside the safe area; adding it would require `env(safe-area-inset-*)` padding on the mobile header, drawer and modals.

**Seasonal opening (Halloween + Canción Criolla):** `AperturaTematica.tsx` (mounted in `App.tsx`) plays `mostrarApertura()` from [src/lib/aperturaTematica.ts](src/lib/aperturaTematica.ts) — a ~2.75 s overlay drawn with plain DOM + Web Animations, no images — only in the installed app (`display-mode: standalone` or iOS `navigator.standalone`), once per launch (`sessionStorage`), and only until `HASTA` (a Lima date). It starts on the manifest's `background_color` with the same icon as `pwa-512x512.png` so it continues the system splash; the icon grows, the bats and maracas come out from behind it, and it all fades over the app. Append `?apertura` to any URL to force it in a normal tab. It honors `prefers-reduced-motion` (just the icon, then a fade). The standalone resource with other color themes and a test page lives in `recursos/apertura-tematica/` (not part of the build); when the season ends, remove the component or move `HASTA`.
